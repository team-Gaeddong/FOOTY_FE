# FOOTY 화면 구현 워크플로

입력: 이 저장소의 GitHub 이슈 번호와 Notion 기능 이름. 둘 중 하나라도 없으면 먼저 요청한다.

## 0. 시작 전 확인 (건너뛰지 않는다)

1. `AGENTS.md`, `docs/harness/decisions.md`, `docs/api/backend-api.md`를 읽는다.
2. 이번 작업에 필요한 미결정 항목을 표시한다. 대부분의 화면 작업은 최소한 다음이 필요하다.
   - FD-01 언어, FD-02 폴더 구조, FD-03 라우팅, FD-08 스타일링
   - API를 부르면 FD-04 서버 통신, FD-06 API 주소·CORS. 로그인·인증이 걸리면 FD-05 토큰 저장
   - 날짜를 다루면 FD-12, 경기 생성이면 FD-13, BE에 아직 없는 API면 FD-14
   - FD-11(테스트 기준)이 미결정이라는 이유만으로 독립 작업까지 멈추지 않는다
3. 필요한 항목 중 `미결정`이 하나라도 있으면 **그 결정에 의존하는 코드를 쓰지 않는다.** `decisions.md`의 `[결정 필요]` 형식으로 결정을 요청하고, 결정과 무관한 작업은 계속한다.

## 1. 요구사항 정리

`docs/harness/sources.md`의 원본 확인 범위를 확인한다. `references/feature-map.md`에서 기능 행을 찾고, 다음을 적어 사람에게 확인받는다(1차 스크럼 회고록 프롬프트 설계 규칙).

- 입력: 사용자 입력 필드와 검증 조건, URL 경로·쿼리
- 출력: 화면에 보여줄 내용, 호출할 API, 성공 후 이동
- 예외 상황: 로딩, 빈 목록, 에러(상태 코드·`code`별), 비로그인·온보딩 미완료·권한 없음, 중복 제출
- 레퍼런스: Notion 기능 설명, BE 엔드포인트·DTO, 디자인(FD-09), 선행 화면

Notion 기능 설명은 대부분 한 줄이다. 설명에 없는 규칙(예: 18명 초과 시 후보 선정 기준)이나 화면 문구를 지어내지 말고 질문으로 남긴다. `xo-rxs/epl`은 같은 도메인의 프로토타입일 뿐 기준이 아니다(FC-06).

## 2. API 계약 대조

- 필요한 엔드포인트를 `docs/api/backend-api.md`에서 찾고, 그 문서의 "다시 확인하는 방법"으로 BE `develop`의 컨트롤러·DTO·에러 코드가 그대로인지 확인한다.
- BE에 필요한 API가 없거나 필드가 모자라면(예: 경기 목록 조회) 그 연동은 멈추고 `decisions.md` 형식으로 보고한다. 응답 모양을 추측해 화면을 맞추지 않는다. 목 데이터 사용은 FD-14 결정을 따른다.
- 스냅샷과 BE 코드가 다르면 BE 코드를 따르고, 스냅샷 갱신을 같은 PR 또는 별도 이슈로 제안한다.

## 3. 브랜치

`footy-git-workflow` 스킬에 따라 `feature/{이슈번호}_{할일}` 브랜치를 만든다. base 브랜치가 미결정(FC-01)이면 확인한다.

## 4. 구현 순서

확정된 FD-02 폴더 구조를 따른다. 확정 전에는 이 단계로 오지 않는다. 각 단계가 끝날 때마다 `npm run lint`로 확인한다.

1. API 호출 함수: 경로·요청·응답·에러를 BE 계약 그대로(FD-04 방식)
2. 상태·훅: 로딩·에러·빈 상태를 포함한 화면 데이터
3. 컴포넌트: 입력 검증은 BE 규칙과 같게(예: 닉네임은 코드 포인트 2~10자)
4. 화면·라우트 연결(FD-03), 인증·온보딩 분기
5. 스타일(FD-08)과 모바일 폭(375px)
6. 테스트: FD-11 확정 전에는 기존 테스트 실행이 필수이고 새 테스트는 권장한다. 사용자·이슈가 요구한 테스트는 반드시 작성한다. 테스트가 없는 경로와 남은 위험을 보고한다

React Compiler가 켜져 있으므로 hooks 규칙과 `react-hooks` 린트 진단을 지킨다. 린트를 `eslint-disable`로 끄지 않는다.

## 5. 검증

```bash
npm run harness -- --mode baseline   # 커밋 전: lint·build
# 커밋 후, 확정된 PR base를 지정해 변경 검사
npm run harness -- --base origin/main
```

위 `origin/main`은 명령 예시이며 FC-01의 결정을 대신하지 않는다. 종료 코드 2(일부 검사)는 완료가 아니다. 실패하면 고친 뒤 다시 실행한다. 원인이 이번 변경 밖에 있으면 고치지 말고 출력과 함께 보고한다.

브라우저 확인:
- 개발 서버: Claude 데스크톱은 `.claude/launch.json`의 `footy-fe-dev`로 미리보기를 연다. 그 밖에는 `npm run dev` 후 `http://localhost:5173`
- 바뀐 흐름을 직접 조작한다. 정상 경로와 1단계에서 적은 예외 상태를 각각 확인한다
- 콘솔 에러·경고가 없는지, 모바일 폭(375px)에서 깨지지 않는지 본다
- 실제 BE와 연동하려면 BE 실행 환경(Java 21, PostgreSQL, Redis, Google OAuth 클라이언트 — BE `README.md`·`AGENTS.md` 2장)과 API 주소(FD-06)가 필요하다. 연동하지 못했으면 그 사실과 대신 확인한 범위를 보고한다

## 6. 커밋과 PR

- 커밋은 의미 단위로 나누고 `footy-git-workflow`의 형식을 따른다.
- PR 본문에 요구사항 표(입력·출력·예외·레퍼런스), 검증 출력, 브라우저 확인 범위, 결정 필요 항목을 넣는다.
- PR 작성 후 `footy-code-review` 스킬로 자체 점검을 한 번 돌리고 결과를 PR 코멘트 초안으로 정리한다. 자체 점검은 사람 승인을 대신하지 않는다.
